# vortex

Georgia Tech's [Vortex](https://github.com/vortexgpgpu/vortex), the open-source RISC-V GPGPU, taken as a black box.

![maturity](https://img.shields.io/badge/maturity-planned-lightgrey) ![license](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0%20OR%20MulanPSL--2.0-blue) ![upstream](https://img.shields.io/badge/upstream-Apache--2.0-lightgrey)

Part of the [Tape-Out](https://github.com/Tape-Out) IP library, wired up by [`xirang`](https://github.com/Tape-Out/xirang). The GPU is a submodule at `third_party/vortex`, on upstream's default branch `master`; nothing in it is modified.

## What this repository adds

Vortex has no Verilog parameters. Its whole configuration is a set of `VX_CFG_*` macros, and two headers generated by its own `ci/gen_config.py`. The manifest's `setup: cfg` task runs the generator for both XLEN settings into `build/vx/`, and writes a Flist per setting that lists every RTL directory as include and library path. The `xlen` knob picks one of the two.

Only XLEN, the raw knobs and the FPU/TCU selectors are passed as macros. Everything else is derived inside `VX_config.vh`, which is left unevaluated on purpose; upstream's `hw/syn/firesim/Makefile` does the same, because passing the evaluated values turns the memory port count into zero.

| Knob | Values |
|:--:|:--:|
| `xlen` | 32, 64 |
| `numClusters` | 1–4 |
| `numCores` | 1–8 |
| `numWarps`, `numThreads` | 2, 4, 8, 16, 32 |
| `l2`, `l3` | on, off |

Two receipt probes run at every point of the matrix: `VX_gpu_pkg::NUM_SOCKETS` must equal `numCores`, and `VX_gpu_pkg::L2_MEM_PORTS` must be at least 1. A projection that is wrong only away from the defaults shows up there.

```console
$ ran run vortex cfg
$ ran test vortex
```

## Limits

Vortex relies on Verilator's leniency in two places: signals used before they are declared, and hierarchical references inside `$bits`. The manifest allows both slang diagnostics. [vortexgpgpu/vortex#418](https://github.com/vortexgpgpu/vortex/pull/418) fixes the first upstream.

The FPU is fixed to the `STD` implementation that upstream picks for ASIC synthesis; `FPNEW` needs the nested `cvfpu`, `DPI` is for simulation and `DSP` for FPGAs. The extensions (TCU, DXA, RTU, graphics, virtual memory, atomics) are not exposed yet. Upstream's own test flow needs its RISC-V toolchain and runtime, and does not run here. The target is FPGA-proven at most: the design has no ASIC memories.
